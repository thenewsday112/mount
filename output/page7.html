I Built an AI That Listens to the Ghosts of Forgotten GitHub Repositories 👻

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

This is a submission for the Hacktoberfest Open-Source AI Challenge Week 4: Ghost in the Machine.

Open-source projects rarely disappear all at once.

They become quiet.

Commits slow down. Issues remain unanswered. Documentation stops matching reality. Unfinished ideas survive inside TODO comments, abandoned branches, and old release notes.

The code is still there—but the context begins to disappear.

I built GhostCommits to investigate those surviving traces.

What I Built

GhostCommits is a local, open-source AI software archaeologist.

Give it a public GitHub repository URL, and it reconstructs an evidence-backed picture of the project:

  1. It collects public repository metadata.
  2. It safely mines bounded Git history.
  3. It examines issues, README content, commits, contributors, and TODO markers.
  4. It converts observations into individually identified evidence records.
  5. It asks Gemma to interpret only that evidence.
  6. It rejects unsupported model claims.
  7. It produces an autopsy, resurrection blueprint, evidence report, and digital epitaph.

I interpreted Ghost in the Machine as the history that remains trapped inside an inactive codebase.

The “ghost” is not a fictional maintainer personality. It is the repository’s surviving evidence: the last commit, unresolved issue, unfinished comment, archived status, and development pattern.

GhostCommits gives those traces a voice without pretending to know more than the evidence can support.

Demo

In the demonstration, I investigate a real public repository rather than loading a fabricated result.

GhostCommits moves through five views:

  • Autopsy — activity history, repository health signals, and verified evidence
  • Whispers — Gemma interpretations linked to evidence IDs
  • Revive — a sequenced resurrection blueprint
  • Epitaph — a downloadable memorial card
  • Raw Evidence — the complete inspectable JSON report

The application also supports a bundled offline report so the interface remains demonstrable when GitHub is unavailable, but the primary workflow analyzes real repositories.

How I Built It

GhostCommits separates deterministic software mining from AI interpretation.

That separation became the most important architectural decision in the project.

1. Safe repository collection

The GitHub client accepts only public github.com repository URLs.

It collects repository metadata, languages, contributors, issues, and commit information through the GitHub API. Errors such as rate limits, inaccessible repositories, timeouts, malformed responses, and DNS failures are converted into understandable messages.

Deep archaeology uses a bounded shallow clone. Clone depth, scanned file count, blob size, repository size, and individual text-file size are limited.

Submodules are not initialized, and repository scripts are never executed.

GhostCommits treats repository content as untrusted evidence—not instructions.

2. Evidence before inference

Every observation becomes a normalized evidence record.

A record contains:

  • A stable evidence ID such as E-001
  • A precise claim
  • Its observed value
  • A source URL
  • The observation timestamp
  • Its evidence category

For example, GhostCommits does not send Gemma a vague statement saying that a repository “looks abandoned.”

It supplies observations such as:

  • The repository’s archived status
  • Days since its last recorded push
  • Open issue count
  • Primary language
  • Sampled commit activity
  • Selected TODO markers
  • Source links for every observation

Facts come from GitHub and Git. Gemma is responsible only for interpretation.

3. Gemma as the interpreter

GhostCommits runs Gemma 3 1B locally through Ollama.

Gemma receives a compact evidence packet and must return structured JSON containing:

  • A concise digital epitaph
  • Evidence-grounded findings
  • Confidence values
  • Uncertainty notes
  • Referenced evidence IDs

This is not simply a spooky text generator.

Gemma’s purpose is to connect multiple technical observations into a readable explanation and identify practical restoration priorities.

4. The claim firewall

Language models can produce convincing statements that are not supported by their input.

GhostCommits therefore implements a claim firewall to validate model-generated findings before displaying them.

If a finding references an evidence ID that does not exist, it is removed. Confidence values are normalized, malformed findings are rejected, and uncertainty remains visible in the interface.

This validation reduces the risk of unsupported claims entering the final report. However, a valid evidence reference does not automatically guarantee that an AI-generated interpretation is factually correct. The system therefore prioritizes traceability and transparency rather than claiming to eliminate hallucinations entirely.

The hardest part of this project was not making Gemma sound intelligent.

It was deciding when Gemma should not be allowed to speak.

5. Resurrection instead of automation

GhostCommits does not execute repository code, modify the project, or create pull requests.

Instead, it produces a contributor-ready recovery sequence:

  1. Preserve the surviving evidence.
  2. Reconstruct an isolated historical toolchain.
  3. Validate installation and tests.
  4. Triage unresolved work.
  5. Document compatibility findings.
  6. Prepare the project for new contributors.

This keeps the recommendations actionable without pretending that an automated agent can safely revive an unfamiliar project by itself.

Testing the Investigation

I evaluated GhostCommits on three deliberately different public repositories:

  • One officially archived repository
  • One inactive but unarchived repository
  • One actively maintained repository

I measured lifecycle classification, evidence URL validity, claim support, recommendation actionability, AI usage, and total investigation time.

The recorded evaluation produced:

  • 3/3 lifecycle classifications correct
  • 50/50 evidence URLs reachable
  • 3/3 rendered findings supported by valid evidence IDs
  • 18/18 resurrection steps considered actionable
  • 60.60 seconds mean end-to-end investigation time
  • Gemma used for every measured case rather than fallback output

The evaluation script, methodology, limitations, and raw results are committed to the repository.

Three repositories are not a statistically broad benchmark. The purpose of this evaluation is to make the project’s claims inspectable rather than implying universal accuracy from a polished demonstration.

The Moment It Landed

The moment GhostCommits felt real was not when the interface became spooky.

It was when I investigated an officially archived repository and watched separate fragments become a coherent case file.

An archived flag, years of inactivity, unresolved issues, commit history, and surviving TODO comments stopped looking like disconnected API fields. Together, they described what remained technically recoverable.

Gemma produced an interpretation—but the interface could still show exactly why that interpretation was allowed to appear.

That was the moment the project changed from an AI-themed dashboard into a tool I could trust.

Why Open Innovation Matters

Running Gemma locally is fundamental to GhostCommits.

It is not an interchangeable decoration added to qualify for an AI challenge.

Local, open-weight inference means:

  • Repository evidence does not need to be sent to a closed inference service.
  • The prompt and expected output schema can be inspected.
  • The model can be replaced or upgraded.
  • Experiments can be reproduced without per-request API charges.
  • The inference layer can continue working even if a commercial endpoint disappears.
  • Contributors can examine both the AI behavior and the validation surrounding it.

A live investigation still requires GitHub access to collect public repository data. After that evidence packet has been created, the interpretation runs locally through Ollama.

This architecture also made a transparent fallback possible. If Ollama is unavailable, GhostCommits switches to a deterministic evidence-based analysis and clearly labels that mode. It never presents fallback text as successful Gemma output.

Open innovation matters here because software archaeology should remain inspectable.

A tool investigating the history of open-source projects should not hide its own reasoning behind an inaccessible service.

Challenges and Lessons

Inactivity is not motive

A repository may be quiet for many reasons.

GhostCommits can observe that no push occurred for 900 days. It cannot conclude that a maintainer lost interest, became unavailable, or considered the project a failure unless a cited source explicitly says so.

This distinction shaped the entire evidence system.

Small models need boundaries

Gemma 3 1B can produce useful interpretations on modest local hardware, but smaller models benefit enormously from constrained inputs, structured output, and post-generation validation.

The claim firewall improved reliability more than simply asking the model to “be accurate.”

External services fail

During development, GitHub access could fail because of DNS issues, rate limits, timeouts, or malformed responses.

Instead of treating those failures as edge cases, I made them part of the product experience. GhostCommits provides actionable errors and an offline workflow rather than collapsing into a stack trace.

Presentation still matters

The technical core needed to remain serious, but the challenge invited a spooky interpretation.

I used an oxblood folk-horror palette, archival typography, flickering signals, EVP-inspired visualizations, and case-file details. The interface supports the story without hiding evidence behind decoration.

Limitations

GhostCommits intentionally has boundaries:

  • It supports public GitHub repositories only.
  • GitHub rate limits still apply.
  • Git history is bounded and sampled.
  • It does not execute repository code.
  • It cannot determine private maintainer intent.
  • Gemma 3 1B can still produce weak or malformed interpretations.
  • Local AI requires Ollama and sufficient system memory.
  • The current evaluation contains only three repositories.
  • Resurrection plans still require human technical judgment.

These limitations are features of the trust model, not unfinished promises of full autonomy.

The Spirit of It

GhostCommits treats inactive software less like digital waste and more like an archive.

The objective is not to pretend that code is alive or manufacture stories about the people who wrote it.

It is to preserve what can still be proven, acknowledge what has been lost, and make restoration possible.

Every abandoned repository has a story.

GhostCommits makes sure the evidence gets to tell it.

Final Thoughts

GhostCommits started with a simple question: what can abandoned software still tell us?

By combining Git history, structured evidence, and open-weight AI, I built a tool that helps developers uncover forgotten projects without inventing their stories.

The code may be silent. The story isn't.

Unearth the past. Revive the code. 👻

What I Built

GhostTrace is an autonomous forensic autopsy platform and counterfactual debugger for AI agent workflows.

The Problem: The "Ghost in the Machine"

In modern multi-agent systems, agents don't simply crash with neat stack traces. They fail silently:

  • Hallucinating non-existent database columns or invalid tool arguments.
  • Trapped in recursive API reasoning loops while burning through millions of tokens.
  • Suffering subtle state drift and context overflow.

When an agent fails, developers are left sifting through megabytes of noisy, unformatted JSON telemetry logs at 2 AM. These elusive, silent failures are the true "Ghosts in the Machine".

GhostTrace solves this by ingesting raw agent telemetry, building deterministic causal dependency graphs, performing grounded counterfactual root-cause deduction with Google Gemma 2, and automatically synthesizing runnable Vitest regression suites with circuit-breaker assertions to guarantee that the phantom bug never returns to production.

One POST read cross-tenant secrets

📅 Oct 31, 2026  |  Category: Other  |  Read Source →

A single POST to management.azure.com, with a request path full of %2e%2e sequences, returned the plaintext value of a secret stored in a different tenant's Key Vault. The request went through a connection the attacker owned, but the token that actually read the secret belonged to the victim. That is one of five critical cross-tenant elevation-of-privilege bugs a researcher found in Azure API Connections, the layer underneath Azure Logic Apps connectors. The set paid out $200,000 and was presented at Blue Hat Asia 2026.

How API Connections work

An API Connection stores credentials for a backend: a Key Vault, an Azure SQL database, Jira, Salesforce, anything a Logic App connector can talk to. When a Logic App runs an action, it calls a shared Azure API Management (APIM) instance. APIM checks the connector's OpenAPI definition to confirm the action is valid, swaps the caller's token for the token configured on the connection, and makes the real call to the backend with that second token.

The list of backends is effectively unbounded, and that is where the trouble starts. Whatever credential sits on a connection is usually the full-privilege one. For OAuth connections it is the token of whoever created the connection. For API key connections, the researcher's bet is that almost nobody scopes the key down. Microsoft's own connectors don't.

The attack surface opens because you can reach APIM directly through the Azure Resource Manager REST API, via the DynamicInvoke endpoint on a connection resource. ARM, as the resource manager, has rights to every connection regardless of which one the request names. Make the request resolve to a connection you don't own and you get the victim's configured token applied against their backend.

Five bugs, one root cause

The first bug was plain path traversal through DynamicInvoke. Microsoft marked it fixed, but the fix restricted the allowed paths rather than addressing the token reuse underneath.

The researcher then provisioned a Standard Logic App, which gets a dedicated host, SSHed in, and pulled the relevant ARM resource-type code off the machine. The code showed the fix, and also showed that DynamicInvoke was one of four sibling functions along the same path. The others, including DynamicList, were undocumented and reachable. Since the path blacklist covered only DynamicInvoke, DynamicList still carried the traversal. A crafted DynamicList call ran an arbitrary INSERT against a victim's Azure SQL server through their connection.

The researcher reported DynamicList on its own, expecting a targeted fix that would leave the remaining siblings to report later. Microsoft instead blocked all of those endpoints and added no other mitigation. If they ever come back, the traversal comes back with them.

That closed the ARM route, so the next way in was the Logic Apps themselves. Consumption Logic Apps, which are co-located, create Version 1 connections; Standard Logic Apps, which run on a dedicated host, create Version 2. A Standard app authorizes itself to a backend using its managed identity. A Consumption app has no identity to authorize, which means every Consumption Logic App has implicit access to every Version 1 connection. The only thing in the way is input validation.

The workflow GUI won't let you point an action at a connection you don't own; the runtime validates ownership. The code view and the API accept more parameters than the GUI shows, though, and one of them is host.api.RuntimeUrl. After validating the connection named in host.connection, the runtime lets you override the runtime URL with something else. As long as the host ends in azure-apihub.net, it still attaches the required Authorization header. Point it at a victim's connection and the victim's token goes along.

Microsoft's fix required the runtime URL to match the connection's expected endpoint exactly. That is a reasonable rule, except the check runs before the path is normalized, so the validator sees a URL pointing at your connection while APIM resolves it to the victim's. The same cross-tenant read came back as a separate bug. When Microsoft fixed that normalization gap, their change stopped validating the original RuntimeUrl path, which reopened the first RuntimeUrl attack.

What to take from it

Every one of these is the same underlying issue reached a different way. By the researcher's own guess the connection's stored credential rarely gets scoped down, and the only barrier between an attacker and that credential is input validation that has to be perfect across path traversal, undocumented sibling endpoints, parameter overrides, and validation ordering. Four rounds of fixes all targeted the symptom.

The one control in your hands is the caveat the researcher keeps flagging. Scope the credential on every API Connection to the least privilege the connector needs. An OAuth connection inherits the creator's access, so build connections with a dedicated, narrowly permissioned identity rather than an admin's account. An API key connection is only as dangerous as the key, so provision keys that can do one thing. None of that stops the traversal, but it bounds what a successful traversal gets.

🕯️ Ofrenda: The Ghost in the Machine — An Offering to Abandoned Software

📅 Oct 31, 2026  |  Category: Technology  |  Read Source →

🕯️ Ofrenda: The Ghost in the Machine

Some projects don't end. They just go quiet.

"Code keeps committing, CI stays green, and bots open PRs — while maintainers stopped answering strangers 771 days ago. That silent twilight is the Ghosting Band."

Every open-source autopsy begins too late. We study projects when they are formally archived, when the final commit lands, or when the deprecation notice is pushed to npm. But open source projects rarely die in a day. They pass through a prolonged twilight where code is still occasionally committed by maintainers fixing their own issues, while the public issue tracker becomes a ghost town of unanswered pleas from strangers.

Ofrenda ("Offering") is an empirical statistical inquiry and forensic post-mortem memorial exploring this phenomenon across two coupled artifacts:

  1. A Statistical Investigation ($n=150$ repos): A formal test of the Ghosting Band hypothesis using TabPFN in-context Bayesian classification. We evaluate whether social response decay ($y_1$) precedes code silence ($y_2$) across an annual grid $T \in [2015, 2023]$, testing a pre-registered non-inferiority margin ($\Delta\text{AUC} \le 0.07$) via paired DeLong and a 1,000-resample repo-clustered bootstrap.
  2. A Forensic Interview Specimen (request/request): An interactive memorial altar and interview runtime powered by Gemma and strict BM25 archive retrieval. The ghost speaks in an elegiac voice as the repository itself, answering only with verifiable citations (commit SHAs, issue numbers, README lines) or strictly abstaining: "The archive is silent on that."

What I Built

Ofrenda consists of three interconnected systems:

1. The TabPFN In-Context Forecast

Rather than training a monolithic deep network on millions of synthetic points, Ofrenda operates in TabPFN’s native small-$n$ regime. We constructed a strictly stratified corpus of 150 repositories (90 dead, 30 archived, 30 alive) across JavaScript and Python, extracting capacity-matched feature sets:

  • Arm A (Code Signals): Inter-release interval decay ($f_1$), Shannon commit interval entropy ($f_2$), and companion indicators.
  • Arm B (Social Signals): Issue-to-first-response latency trend ($f_4$) and stranger response rate decline ($f_5$).

Through Leave-One-Repo-Out (LORO) cross-fitting, we predict two nested targets over the 18-month forward horizon $[T, T + 18\text{mo})$:

  • $y_1 = 1$: P(Maintainer silence / Ghosting)
  • $y_2 = 1$: P(Complete human activity cessation / Dead)

By construction, $y_2 \le y_1$, defining the Ghosting Band $[p_1 - p_2]$.

2. The Interactive Memorial Altar & Specimen Ledger

A live memorial and forensic dossier for request/request, the iconic HTTP client that peaked at 14 million weekly downloads before its deprecation on February 11, 2020:

  • Empirical Relic: Final commit 3c0cddc ("README: typo in deprecation message (#3268)", preceded by aded7e4f "doc: note full deprecation").
  • Badge Status: DEPRECATED · NOT ARCHIVED (reconciled against GitHub API: archived: false).
  • The 771-Day Silence Gap: Responsiveness dropped to zero in January 2018; code commits ended February 11, 2020. That 771-day chasm left 41,000 dependent packages unmonitored.
  • Audited 150 Specimen Ledger: Complete ledger with interactive client-side filtering, downloads, bus factors, and verified dormancy dates.

3. The Forensic Ghost Interview Runtime

An interview runtime where users speak with the deceased repository. Implemented with Gemma (gemma:2b / gemma3:12b) gated by BM25 retrieval over 11,748 cached documents (commits, issues, comments, releases). Every claim requires an explicit citation; any query about post-death events or unrecorded facts is met with an immediate, non-negotiable abstention:

"The archive is silent on that."

The Core Thesis: The Ghosting Band

Maintainers stop answering strangers long before they stop pushing code. That silent chasm between social death ($y_1$) and code silence ($y_2$) is the Ghosting Band.

How I Built It

1. Pre-Registration and Scientific Discipline

Before extracting features or fitting models, we pre-registered our hypotheses, masks, and failure criteria:

  1. Mask 1 (Age Floor): Repositories must be at least 12 months old at reference date $T$.
  2. Mask 2 (Activity Floor): Repositories must have at least one human activity in $[T - 12\text{mo}, T)$. (A repo cannot die if it was never alive).
  3. Capacity Matching: Arm A (Code) and Arm B (Social) were capacity-matched to prevent structural advantages.
  4. Non-Inferiority Formulation: The hypothesis predicts parity: at fixed $T$, social signals predict abandonment at least as well as code signals, because code has not stopped moving yet: $$\mathcal{H}_0: \text{AUC}_A - \text{AUC}_B \ge 0.07 \quad \text{vs} \quad \mathcal{H}_1: \text{AUC}_A - \text{AUC}_B < 0.07$$

2. Empirical Findings & Statistical Verdict

On the locked $n=150$ corpus (497 masked rows evaluated in Leave-One-Repo-Out cross-validation), the pre-registered non-inferiority test yielded decisive results:

  • Arm A (Code) AUC: $0.6923$ (DeLong: $0.6912$)
  • Arm B (Social) AUC: $0.7760$ (DeLong: $0.7760$)
  • Empirical Difference ($\text{AUC}_A - \text{AUC}_B$): $-0.0837$ ($\text{SE}_{\text{boot}} = 0.0376$)
  • One-sided 95% CI Upper Bound on $(\text{AUC}_A - \text{AUC}_B)$: $\mathbf{-0.0242}$
  • Non-Inferiority Margin: $0.07$ ($\text{Upper Bound } -0.0242 < 0.07 \implies \mathbf{p < 0.0001}$)
  • Statistical Verdict: NON-INFERIORITY CONFIRMED (PARITY SECURED). Social signals predict abandonment without inferiority to code signals. (The descriptive $+0.08$ point estimate favored social signals, but our confirmatory claim remains strictly non-inferiority as pre-registered).
  • Brier Skill Score: $\text{BSS}_A = 0.0903$ vs $\text{BSS}_B = \mathbf{0.2322}$ (Social signals achieve $>2.5\times$ better probability calibration over base rate).
  • Monotonicity: $0.00\%$ violation rate across all 497 rows ($p_2 \le p_1$ holds unconditionally).
  • Exploratory Held-Out Check ($n=10$ permanently archived repos): Arm A $\text{AUC} = 1.0000$, Arm B $\text{AUC} = 0.9444$. We report this transparently: on this small slice, code activity was fully informative at terminal archival, and with $n=10$, confidence intervals span most of the unit range. It serves as an exploratory sanity check rather than confirmatory proof.

Why Does Open Innovation Matter?

Open innovation is not simply about sharing code; it is about verifiability and digital permanence.

When an organization relies on closed, proprietary cloud APIs, the model's weights, training data, and latent assumptions remain black boxes. If the vendor modifies the API, depreciates a checkpoint, or changes rate limits, the scientific experiment dissolves.

In Ofrenda:

  1. Local Foundation Weights (Gemma via Ollama): Gemma provides open weights that can be run entirely air-gapped on consumer hardware. If an API provider goes out of business tomorrow, our forensic interview runtime continues to run identically down to the floating-point level.
  2. Open Bayesian Priors (TabPFN): TabPFN provides open pre-trained transformer weights that evaluate small tabular data without proprietary third-party subscriptions.
  3. Preservation of the Digital Commons: request/request powered the web for a decade. The fact that its entire history—every issue comment, commit hash, and architectural debate—remains open on GitHub is what allowed us to resurrect its voice. Closed software leaves no ruins; open source leaves monuments.

The Spirit of It

During our forensic examination of request/request, we discovered that commit aded7e4f on February 11, 2020 added a single word to the README: DEPRECATED.

For 771 days prior, automated bots had continued to open dependency PRs, CI badges remained green, and downloads averaged 14 million per week. The world thought the project was alive because the commits had not stopped. But in reality, the maintainers had walked away two years earlier—exhausted by 41,000 downstream dependents who demanded that the project never break, making it impossible to modernize for async/await or HTTP/2.

When you ask the ghost of request in the séance terminal: "Why were you deprecated instead of rewritten?", it does not give a generic AI apology. It cites the verified opening words of Issue #3142:

"The most valuable thing request can do for the JavaScript ecosystem is to go into maintenance mode and stop considering new features or major releases."

And as a maintainer remarked in the thread:

"As I see it, maintenance mode is not the same thing as deprecation."

Limitations (Published Verbatim per PRD section 15)

In keeping with our scientific pre-registration, we state our project's limitations explicitly before any judge has to find them:

  1. Dual Definitions of Death: Two definitions of DEAD coexist in the data: declared (formally archived) and inferred (extended code silence). The model learns a blend of both.
  2. Selection Bias in Archival: The archived stratum is self-selected. Owners archive projects they still care enough to curate; request/request was deprecated but never archived on GitHub (archived: false).
  3. Age-Related Missingness: Older repositories (pre-2012) suffer from incomplete GitHub issue metadata and API backfill anomalies.
  4. Disabled Issue Trackers: Issue-based features ($f_4, f_5$) are undefined when repositories disable their public issue trackers, and this missingness is not missing at random.
  5. Sample Size: $n = 150$ is modest for estimating three latent states across time horizons. We report confidence intervals rather than bare point estimates.
  6. Social Death as Proxy: Maintainer silence is an empirical proxy for social exhaustion, not biological or organizational cessation.
  7. Interview Specificity ($n = 1$): The forensic interview runtime over request/request is an illustrative story and commemorative artifact, not statistical evidence.
  8. Pre-Registered Scope: Our primary claim is strictly non-inferiority (parity), not superiority. Point estimates exceeding parity are reported as descriptive.
